# 金融研发 AI 工作台方向
> **摘要**: 基于 nanobot 探索面向金融研发团队的可审计 AI 同事工作台，首个试点聚焦证据驱动的缺陷排查。
> **创建日期**: 2026-07-25
> **最后更新**: 2026-08-30

## 1. 当前判断

建议将 nanobot 作为 Agent Runtime 基座，逐步封装面向研发流程的 AI 同事。产品不应先做一个通用的“多智能体平台”，而应先完成一个真实、可复盘、可衡量的研发闭环，再决定是否扩展更多 Agent。

推荐定位：

> **基于研发证据的任务协作与风险辅助工作台。**

多智能体是内部编排方式，WebUI 是任务观察、人工确认和审计入口，CLI 仍是适合 CI、Linux 节点和离线环境的可靠入口。

## 2. 目标用户和价值

首批用户包括开发、测试、评审和运维/安全人员，重点帮助他们：

- 根据日志、测试输出和 Git 变更定位问题；
- 生成回归测试和风险审查清单；
- 理解项目结构、调用关系和版本演进；
- 复用经过验证的团队知识和排障方法；
- 查看 AI 使用了哪些证据、工具、模型和规则。

AI 只提供分析、验证建议和变更准备材料，不替代代码评审、测试、发布和生产操作审批。

## 3. 首个试点：缺陷排查助手

输入可以是工单描述、脱敏日志、失败测试输出、Git commit 或人工粘贴的错误信息。首版只面向非生产、边界清晰的项目，默认使用 `observe` 模式。

建议流程：

```text
问题输入
  -> 证据清单
  -> 只读证据采集
  -> 事实和候选原因
  -> 验证计划
  -> 白名单验证（可选）
  -> 影响范围和处理建议
  -> 人工确认
  -> 报告、证据包和审计记录
```

报告必须区分：

- 已观察事实及证据位置；
- 有证据支持的推断和候选假设；
- 缺失信息与不确定性；
- 已执行和未执行的验证步骤；
- 影响范围、回滚建议和升级责任人。

不能仅凭一段日志宣称根因已确定或问题已修复。涉及生产环境时只生成建议和审批材料，不执行命令。

## 4. Agent 的封装方式

一个 Agent 应是可登记、可版本化的能力包，而不只是一个 Prompt。至少需要声明：

- 名称、版本、维护人和适用项目；
- 使用的模型或模型预设；
- Skills、规则和输出报告格式；
- 可用工具、工作区范围和运行模式；
- 依赖的插件/适配器及回滚方式。

排障 Agent 内部可以包含有限的职责：任务编排、证据采集、分析、验证和报告。确定性工具优先承担 Git、日志解析、构建和测试，不让多个模型重复猜测同一问题。

后续可按同一机制扩展：

- Merge Request 风险审查；
- 测试设计和回归清单生成；
- 项目地图、模块卡片和版本时间线；
- 数据库迁移与发布准备审查；
- 安全配置和敏感信息检查；
- 项目文档与知识资产维护。

是否开发这些 Agent，应由首个试点的实际效果决定。

## 5. Skill 的积累方式

Skill 是流程知识、报告规范和领域经验的版本化资产。不能让 Agent 自动修改 Skill 后立即生效，应建立以下闭环：

```text
历史任务和报告
  -> 人工确认结论
  -> 提取重复模式
  -> 生成 Skill/规则草稿
  -> 使用评估样本验证
  -> 审批发布
  -> 观察误报、漏报和回滚情况
```

每个 Skill 至少记录适用范围、输入输出、依赖工具、禁止事项、示例案例、测试样本、版本和维护人。模型记忆不能替代 Git、项目文档和原始证据。

## 6. WebUI 形态

WebUI 不应只是聊天页面，首版应作为本地或内网的任务控制台，展示：

- Agent、项目、运行模式和任务状态；
- Agent/工具执行时间线；
- 证据文件、来源、哈希和访问范围；
- 当前假设、验证步骤、退出码和输出摘要；
- 报告预览、JSON/Markdown/证据包；
- 补充证据、重新运行、确认和驳回操作；
- 模型、Prompt、Skill、规则和插件版本；
- 审计事件和失败原因。

聊天可以作为任务入口，但不能成为唯一的事实载体。任务、步骤、证据、报告和审计记录应有稳定的数据结构，并可从 CLI 和 WebUI 访问。

## 7. 约束和安全边界

- 代码、日志和数据库导出物默认敏感，先分级、脱敏、限长，再交给模型；
- 默认使用内网或本地模型，禁止静默转发公网模型；
- 首先支持文件和离线导出物，不直连生产数据库；
- 工作区只读优先，构建和测试仅允许白名单命令及临时目录；
- 生产环境不开放 `apply`，不自动合并、发布、评论或修改外部系统；
- 插件必须有来源、版本、哈希、依赖、权限声明和回滚方式；
- 每次任务记录输入摘要、工具调用、命令摘要、模型、规则、输出哈希和人工结论；
- 报告绑定 Git 范围和输入哈希，源数据变化后标记为过期。

建议保留四种运行模式，但先只开放前两种：

| 模式 | 能力 | 首版状态 |
|---|---|---|
| `observe` | 读取材料并生成报告 | 默认开放 |
| `verify` | 执行白名单构建/测试，写临时目录 | 试点评估后开放 |
| `propose` | 生成补丁或操作单，不执行 | 后续评估 |
| `apply` | 执行已登记的低风险动作 | 暂不开放生产 |

## 8. 现有基础和待补能力

nanobot 已有 `spawn`、持续目标、Skills、CLI Apps、工具插件、MCP、Provider、workspace scope、沙箱和 WebUI runtime events，可作为实现基础。核心 Agent Loop 和 Runner 应保持小幅改动，领域能力优先放在工具、Skill、适配器和 WebUI 层。

要形成工作台闭环，还需要补充：

- Agent Profile 注册、版本和权限模型；
- 任务、步骤、证据包、报告和审计记录；
- 人工确认、阻塞和重新运行机制；
- 结构化排障报告 Schema；
- Skill/规则的测试、审批、发布和回滚；
- CLI 与 WebUI 共用的任务查询和事件协议；
- 脱敏、出站策略和模型调用记录；
- 基于历史缺陷的评估集。

这些是候选建设项，不代表当前仓库已经具备完整业务能力。
