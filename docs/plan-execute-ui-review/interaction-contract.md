# 自然任务拆解交互契约

本文件记录方向 A 第二轮 UI 评审后的交互语义。它是后续实现依据，不代表当前生产代码已经支持。

## 产品心智

系统不向用户暴露 `react` 与 `plan_execute` 两个互斥模式，也不提供“进入计划模式”“关闭模式”或“取消计划”的常驻按钮。LLM 仍处于连续对话中：遇到简单问题直接回答；遇到需要多步工具调用、跨文件修改、研究或验证的任务时，自然创建结构化任务列表；任务变简单或目标变化时，自然收敛、调整或结束任务列表。

任务抽屉是对 LLM 当前工作状态的透明展示，不是独立项目管理器。用户不需要学习另一套操作语言。

## 调度与用户打断

用户消息始终优先于调度新的任务步骤。正在执行的不可安全中断工具可以完成当前原子操作，但系统不得在未处理用户消息前继续启动下一步。收到用户消息后，LLM 获取最新任务列表和执行结果，再决定：

- 回答问题后继续原任务；
- 修改任务描述或顺序；
- 新增任务；
- 将任务标记为完成、取消、阻塞或不再需要；
- 放弃剩余任务并回到普通对话；
- 对含义不明确的指令向用户澄清。

WebUI 输入框在任务执行期间保持可用。发送打断消息后显示“正在处理你的更新”，任务抽屉暂时不启动新步骤。

## 结构化任务工具

LLM 通过宿主提供的任务工具操作列表，不能只在自然语言中声称状态已经改变。建议工具边界：

- `create_task_list(objective, tasks)`：在确有多步执行需要时创建任务列表；
- `update_task(task_id, status, note, evidence)`：更新单项任务状态；
- `replace_tasks(revision, tasks, reason)`：目标变化时调整未完成任务；
- `finish_task_list(summary)`：所有必要任务结束后归档任务列表。

工具必须使用稳定 `task_id` 和乐观并发 revision，避免旧调用覆盖用户打断后的新状态。

## 用户已手动完成工作

例如用户说：“测试我已经手动跑过了，结果通过。”

1. 用户消息优先进入当前对话轮次；
2. LLM 将“测试”与当前任务列表中的候选任务匹配；
3. 唯一匹配且语义明确时，调用 `update_task` 将其设为 `completed`，note 记录“由用户手动完成”，evidence 记录用户陈述；
4. 若存在多个测试任务或结果含糊，LLM 先询问具体是哪一项，不猜测；
5. 工具成功后，WebUI 原位更新任务状态，并显示一条轻量反馈：“已根据你的更新完成『运行完整测试』”；
6. LLM 重新评估依赖关系，再决定继续哪个任务。

用户说“这个不用做了”“先别处理部署”“文档不用更新”等情况采用相同流程，由 LLM 根据语义调用工具标记 `cancelled` 或调整列表。取消单项任务是任务状态，不等于关闭一种全局模式。

## UI 呈现

输入框上方使用紧凑任务条，展示当前任务、完成数量和总体进度。点击“展开”查看完整任务列表。抽屉默认只读，不显示暂停、关闭模式、取消计划、步骤菜单等管理按钮。

任务状态包括 `pending / running / completed / cancelled / blocked / failed`。取消项保留在列表中，以删除线和“已取消”文本表达。用户打断后，当前运行项可短暂显示“正在根据你的消息更新任务”，随后由服务端权威状态替换。

任务完成或不再相关后，任务条自动淡出；计划摘要作为会话历史中的轻量记录保留，不在输入框长期占位。

## 实时同步

前端通过 WebSocket 接收任务列表快照和增量事件。事件包含 `task_list_id`、`revision`、`task_id`、`status`、`updated_at` 和可选 evidence。状态变化原位更新，不为每次进度制造普通聊天消息。用户引发的任务状态变化可显示一次短暂反馈，但不要求确认弹窗。
